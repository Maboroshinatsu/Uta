## 验收结论：部分通过

原 11 项中，**10 项在本轮代码、组件脚本、隔离模块和发布包核对范围内通过**；**[P1: 安装超时后的互斥保护] 在同一 profile 内有效，跨 profile/实例仍不完整**。因此不能把该批修复标成整体通过，也不建议据此提升 stable。

本轮 13 个修复验证用例均通过；另一个跨实例边界探针复现了安装互斥缺口。自动测试和这些受控探针不等于真实 UI、宿主握手、声音或干净机器验收。

## 尚未通过：[P1: 安装锁按 Uta profile 保存，不能保护共享的 Codex 配置]

代码位置：`app/src/main/host-onboarding.ts:649–654、681–691、830–859`。

本版把超时阻断持久化到 `deps.runtimeDir/host-install-block.json`；进行中锁和阻断状态也是每个 service/进程独有的变量。Uta 的日常实例和候选实例有不同 runtimeDir，但默认可能使用同一个 `CODEX_HOME`。因此隔离了 Uta 数据，并没有隔离宿主安装所修改的资源。

复现步骤：

1. 在独立临时目录创建一个 Codex 配置目录和插件资源，构造两个生产 `createHostOnboarding()` service。
2. 两个 service 使用同一个 Codex 可执行路径和 `CODEX_HOME`，分别使用 `daily-profile`、`candidate-profile` 两个 runtimeDir。
3. 第一个 service 的市场写入命令返回超时、`stillRunning:true`，产生阻断文件。
4. 调用另一个 service 安装。它没有读到第一份阻断，也不共享内存互斥，仍调用市场写入命令。

结果：同一 `CODEX_HOME` 的市场写入命令被调用 **2 次**，两个返回均为“进程没有确认退出”。该边界不是单实例重复点击；本版新增的单实例/同 profile 重启阻断确实有效。

证据：忽略目录 `.tmp/acceptance-alpha11-20261025/boundary.cjs` 和 `boundary-result.json`。实际执行了生产安装模块与临时文件系统，命令执行结果使用受控替身；没有启动真实 Codex 安装进程，没有写真实宿主配置，也没有观察到真实配置损坏。探针证明的是第二次写入入口未被挡住；并行写入和失败回滚覆盖其他实例结果是实际使用时的风险。

建议：

- 以规范化后的 **Codex 配置目录** 为共享资源建立跨进程互斥；同一宿主目录无论从哪个 Uta profile 安装，都须竞争同一把锁。
- 安装中原子获取锁；旧写入者未确认退出时保留共享阻断。仅把现有文件挪到共享目录仍不够：活实例也必须重新检查共享状态，不能一直依赖启动时的内存快照。
- 解除阻断要对应同一宿主目录、正确锁所有者和清晰的人工恢复步骤；持久化失败不得声称重启仍安全。
- 验证两个实例共用宿主目录、不同宿主目录互不阻塞、任一实例重启、超时/失败回滚，以及解除阻断后的恢复。正确预期为第二个实例的写入命令调用次数 **0**。
