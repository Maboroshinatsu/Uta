## 1. 1.0.0 到底要交付什么

Uta 是 Windows 上常驻桌面的角色伴侣。用户解压 ZIP、打开 Uta.exe，就能看到角色、配置自己的模型与语音、连接 Agent 平台，并在工作过程中得到自然且克制的回应。角色表现、设置操作、数据保留和安装升级应当像同一个产品。

1.0.0 的重点是把已经存在的功能做完整，特别是 Live2D 表现。不是把所有参考项目的功能都搬进来。

| 使用场景 | 1.0.0 必须做到 |
| --- | --- |
| 首次启动 | 无开发环境也能运行；看到默认角色和简单引导；离线也能打开设置和播放本地动作；首次默认静音 |
| 日常桌面 | 桌宠保留托盘图标，设置是普通独立窗口；可隐藏、恢复、拖动、缩放、穿透；普通宿主事件尊重用户隐藏的选择 |
| 设置 | 六个领域各管各的事；同一个设置只有一个主要编辑入口；保存、失败、冲突和未保存内容明确 |
| Live2D | 表情、动作、视线、眨眼、呼吸和口型可以协调共存；取消、换模、切会话后不残留；表现强度可调，安静模式可用 |
| 连接 Agent | 看得出插件是否加载、Uta 是否在线、绑定哪个会话；消息到达和角色执行分开显示；断开、过期和不支持的能力说明清楚 |
| 语音 | 至少一条本地 TTS 与一条云端 TTS 路线实测可用；试听有结果，取消有效；语音失败不会假装成功；STT 默认先填入输入框 |
| 工坊 | 用户可以预览、撤销、保存、恢复；预览不自动保存；退出或崩溃会释放对角色的控制；旧预设可以继续使用 |
| 模型 | DS 鼠控版作为主要表现与分发基准；Hiyori、缺能力模型和静态立绘用于兼容验证；缺失能力时保守降级 |
| 升级 | 更新程序保留设置、模型与预设；迁移前备份，可恢复；候选版通过验收后才替换日常启动目标 |
| 排错 | 用户能复制一份不含密钥、聊天正文和个人敏感信息的诊断摘要；普通错误能说明下一步怎么做 |

### 1.0.0 范围之外

PIXI/Cubism 大版本替换、VRM/3D、摄像头面捕、MAGIC 训练、强制五元音口型、系统音频捕捉、账号与云同步、模型市场、独立大模型聊天、复杂记忆系统，以及全天无人值守开发调度器均不作为 1.0.0 的前置条件。它们可以作为后续实验，不能挡住现有产品交付。

跨平台桌面系统暂不承诺；首版发布目标为 Windows x64。具体支持的 Windows 版本在兼容测试后写入发布说明，不能用开发机一次运行代替系统支持承诺。

| 发布 | 干净源码打 ZIP、来源清单与 hash、日常版本登记已存在 | 新功能没有进入日常包；默认模型分发、迁移、普通电脑安装路径与候选回滚尚需交付 |
| 测试 | 最近记录为应用 571 项中 566 通过、5 跳过；插件此前 104 项通过 | 这是已有记录，本次没有重跑；五项 DS 真实样本检查不能算通过；部分 UI 测试复制逻辑而没有执行实际组件 |

**判断：项目已经有产品雏形，不需要再从“搭基础框架”开始。第一优先是把现有独立设置中心做可靠；第二优先是让新的 Live2D 控制在 DS 上产生可见差别。** 两项应尽早交替展示，不必等所有设置重画完才动角色。

## 3. 开发方式：每一轮都能看见结果

### 3.1 一轮工作的固定流程

1. 任务开始用两三句话说明：改什么、完成后到哪里看、怎样判断有效。确认过的方向直接执行，不反复讨论。
2. Codex 在统一开发目录串行完成实现；只有确需隔离的迁移、构建或验收才使用单独目录，完成后合回。任务中尽早提供真实接线或临时开发入口；演示数据必须标清。用户能打开的程序及其数据目录始终明确。
3. 完成一个可操作变化后展示：新旧对比、操作步骤、截图或短录屏。底层任务若必须单独做，必须说明它将解锁哪一个可见功能，并与对应界面/角色演示安排在同一版本。
4. 跑受影响的测试和必要的类型检查/构建，说明实际运行了什么；界面与有声功能另外实测。
5. Codex完成复核与验证后提交到统一开发版，进度入口更新为“待你体验”或“已验收”；版本结束交 ZIP 候选。

不再把几十份 progress/result 或 CLI 原始日志作为用户的主要进度入口。开发交接保留必要细节，但用户只需查看下面这张卡片。

### 3.2 用户进度卡片

每次汇报只更新以下内容，不使用单独的事项代号：

| 字段 | 示例（格式示例，不是当前已完成事实） |
| --- | --- |
| 当前目标 | 设置保存可靠 |
| 已完成 | 修改主题后，宠物同步变化，重启仍保留 |
| 现在在做 | 保存途中再次编辑时保留新输入 |
| 到哪里看 | 指定程序/脚本完整路径 + 实际环境名称 |
| 你怎样验收 | 修改颜色→保存→重启→确认一致 |
| 阻碍或选择 | 无；或明确一个具体问题及影响 |

状态只使用：未开始、进行中、待审查、待你体验、已验收、受阻。每项都写完整任务名。测试项数、改了多少行和花了多少 token 不作为完成百分比。不能用“已完成80%”隐藏还不能使用的关键步骤。

### 3.3 三种程序各只有清楚的用途

- **日常程序**：用户已验收的解压版 Uta.exe，继续使用正式数据。
- **正在体验的开发程序**：固定为统一开发目录的程序，使用独立开发数据；允许热更新。临时验收实例由 Codex 按需使用并收尾，不形成另一条开发线。
- **候选程序**：每个版本末尾交可解压运行的 ZIP，先使用隔离数据或明确选择的正式数据副本验收。用户认可后再提升为日常版本。

启动入口必须显示版本/源码提交、数据环境、端口和是否为日常程序；高级路径放展开项。不得整体替换 APPDATA，也不得遇到目标不可用就连接别的 Uta。

## 4. 从当前版本到 1.0.0 的顺序

以下是交付顺序，不是固定工期。每个版本可有多个小演示；版本号在实际形成候选包时登记，不因写完计划就修改 package.json。

| 版本与目标 | 你会得到什么 | 离开本阶段的条件 |
| --- | --- | --- |
| 0.2.0 设置中心真正可用 | 一个清楚、保存可靠、可从正式解压版打开的设置中心 | 草稿/冲突/旧数据迁移/窗口恢复通过，交解压候选 |
| 0.3.0 DS 上看得见的新控制 | 表情、眨眼与口型不互相争抢；可比较旧/新效果 | 新旧受控对比、范围/取消/换模通过，保留回退 |
| 0.4.0 连贯的日常表现 | 自然待机、情绪过渡、任务状态回应与安静模式 | 固定脚本中自然、克制，不重复抖动、不虚报任务结果 |
| 0.5.0 语音完整可用 | 配置→保存→试听→实际播报→停顿/取消都可理解 | 真实有声 TTS、口型结束、STT草稿与权限失败通过 |
| 0.6.0 四个平台连接可靠 | 安装、发现工具、绑定会话、看到角色回应的引导 | Codex/Qoder/Antigravity/DSH 各有真实能力矩阵与记录 |
| 0.7.0 模型与工坊完整可用 | 模型切换、能力提示、校准、预设预览/撤销/保存 | 换模失败保留角色，工坊退出释放，旧预设保留 |
| 0.8.0 体验与运行质量 | 六领域视觉统一、普通电脑可用、占用与错误有控制 | 可访问性、窗口/DPI、性能、IPC与资源边界检查完成 |
| 0.9.0 公开测试候选 | 含默认模型、引导、说明、升级与回滚的完整ZIP | 干净电脑/升级副本、长时间运行、外部体验问题闭环 |
| 1.0.0 正式发布 | 用户愿意长期使用且有明确支持边界的版本 | 第10节全部门槛满足，用户验收候选，登记并交付正式包 |

0.2 的界面整理与 0.3 的模型观察工具可以分小步交替推进，由 Codex 串行实现并展示。0.3 的真实渲染接线需要验证实际写入顺序，0.4 不应在新控制尚不稳定时堆动作。0.6 的已有插件问题可随时修复，但大范围扩展平台不抢占前面的主要产品目标。

- Codex 同时负责实际页面的状态逻辑与交互整理，先解决输入丢失，再整理展示。
- 处理 `SettingsWindowApp.vue`：保存一份打开/上次保存时的基准、逐字段草稿与编辑版本。远端变化先与基准比较，再更新已提交快照；没有本地编辑的字段可同步，有本地编辑的字段保留并提示。保存回执只清除本次提交对应的编辑，不能清除后来输入。
- “覆盖保存”应先展示真正冲突的字段。重试期间出现第三次修改时继续提示，不能无限自动覆盖。关闭、重开与切领域保留/放弃草稿的行为一致；点击关闭时未保存内容给明确选择。
- **可见验收**：改主题但不保存，另一入口改音量；主题草稿保留、音量同步；保存失败后输入保留；慢保存期间再改颜色，旧回执不吞新颜色。必须运行实际组件/状态控制器，不能在测试里复制一份理想算法。

**[SET-02：六领域去重与保存规则统一]**

- Codex 实现。保留已确认的蓝色强调 Bento，逐领域替换旧嵌套页，不一次重写整个设置中心。
- 角色与动作只放模型、表现、预设与工坊；连接与会话只放平台、会话及连接引导；语音只放 TTS/STT；桌面与交互放窗口、穿透、快捷键；外观与性能放主题、帧率与安静/节能偏好；关于与诊断放版本、资料与排错。
- 同一个 TTS 总开关、provider、音量不再同时出现两套。默认移除系统语音入口，遵循项目此前只提供本地/云端的产品方向；历史值保留并提示选择，不悄悄换声音。若用户以后明确恢复系统语音，另作方向变更。
- 保存规则：主题/显示等安全偏好统一即时保存且显示失败；服务配置和工坊使用草稿与明确保存。迁移过程中可以暂时保留旧区块，但每个区块必须明确自己的保存方式，不能顶部“保存偏好”让人误以为能保存整页所有内容。
- 首屏只放常用项，详细参数折叠；“公开偏好字段、契约、revision、Profile”等信息移到开发详情。显示真实运行环境名称，替换固定的“开发环境”占位。
- **可见验收**：用户能在一个入口找到模型、连接、语音与窗口设置；不会遇到同一个开关不同值；1024×640和系统125/150%缩放下主要操作能找到。

2026-10-24 进展：语音页仅保留一套公开播报偏好；旧连接页中的 TTS/STT 表单改为跳转，不再出现重复控制。服务连接使用现有 Bento tokens 单列呈现，音量/语速补标签；保存方式分别说明。新增系统语音选项移除，已有 system 值保留并提示选择。STT 仍为旧组件，其他领域及缩放/键盘全面验收待后续；不把语音去重当作六页重构完成。

后续进展：设置外壳补了小窗口布局、可聚焦主题按钮、公共开关名称/标签关联、选择状态与焦点；切分区回到顶部。真实 Electron 六页 × 六组窗口/渲染缩放共 36 个布局检查通过，键盘切主题/开关/保存与关闭弹窗焦点通过。应用 707 通过/5 跳过，类型与构建通过。只覆盖本轮公共控件和可达性，不宣称旧工坊所有控件或 Windows 系统 DPI/读屏器均已认证。

**[VOICE-03：录音输入与设备失败]** — Codex 负责交互与接口。真实麦克风权限、设备缺失、录音中、转写中、取消、无语音都能理解；默认先填草稿，用户明确开启后才自动发给已绑定宿主。切会话/关窗停止录音。敏感内容不进日志。实测不能用合成音频代替真实录音验收。

**可见验收**：用本机可用的一条本地TTS和一条云端TTS真实听音；暂停、取消、换服务、断网、凭据错误和设备拒绝逐项验证。初始参考目标：首帧口型偏差≤100ms、结束闭合≤300ms；这是待测目标，记录方法和失败原因，不能用预期值填实测结果。

## 6. 设置的数据归属

目标是每类数据只有一个明确保存者，而不是机械地把所有东西塞进同一个JSON。

| 数据 | 目标归属 | 用户能理解的行为 |
| --- | --- | --- |
| 主题/行为/音量等偏好 | 主进程版本化公开设置 | 改动自动保存，失败显示；双窗口一致 |
| 服务普通配置 | 主进程版本化服务配置，按provider保留草稿/已保存值 | 先测试再保存，切服务不丢草稿 |
| API密钥 | 主进程安全存储，渲染层只见是否已配置 | 可替换/清除，不回显、不导出明文 |
| 位置/尺寸/置顶/穿透 | 窗口设置服务 | 重启恢复，布局异常可重置 |
| 宿主选择/安装路径 | 主进程连接配置 | 明确目标，失败不改连别的会话 |
| 模型预设/映射覆盖 | 按内容签名划分的用户配置 | 换模互不污染，源资源与用户编辑分开 |
| 运行中的会话/语音/动作 | 内存运行状态，必要的短期端点文件 | 取消和退出清理，不当作长期用户设置 |
| 开发任务日志 | 仓库外operations | 用户应用不依赖这些文件才能正常运行 |

每次迁移都应交字段清单、旧来源、优先规则、备份、失败状态与实际恢复步骤。旧来源保留多久与清理入口在迁移任务中明确，禁止未经确认自动删除。

## 7. Live2D参考项目怎么用

- **Uta负责最终控制**：模型身份、控制来源、释放、旧预设兼容与最终写Core的边界由Uta掌握。当前mixer是基础，不能自动等同完整表现系统。
- **Soullink**：现有ADR接受隔离试验，未批准产品默认引擎。先参考其连续情绪、种子化自然动作和资源组织方法。若以后引入公共engine，必须另开有演示的对比任务，证明嘴部门控/取消/owner缺口已处理；不复制整套renderer或靠内部API解决。
- **AIRI**：吸收阶段明确的更新、owner释放、弹簧/dt保护和语音结束交接。MAGIC保留为后续实验。现有研究针对登记的本地源码，不能宣传成持续跟随上游或任意模型都支持五元音。
- 参考实现与模型素材的许可分别登记。实际复制代码时记录来源、版本、许可证和修改；功能相似不等于可以省略来源核对。

## 8. Codex 统一开发与会话交接

Codex 负责实现全部功能、测试、复核、整合、演示和交接。用户负责产品方向、直接体验和最终日常版本验收。Qoder / Antigravity 不再持有默认实施任务；DSH 仍仅是兼容性测试对象。需要重新分工时，由用户明确授权，不能从历史计划推导授权。

同一时刻只推进一个可以展示的小目标。主目录是统一开发版；不为每个平台预开分支、任务目录或独立开发实例。确需隔离的迁移或验收可临时使用一个 Codex 目录，完成后验证并合回主目录，不让用户在多个目录中寻找最新效果。

Codex 额度不足或会话结束时，先提交已经验证的完整改动，把未完成工作、测试结果、实际运行环境和下一步写进 `workflow/HANDOFF.md`。保留 `workflow/CURRENT.md` 为简短进度入口。下一会话先读两份文件并核对 Git 现场，不自动派给其他平台、不启动旧 CLI 或恢复历史监听。

交接的目标是任何后续会话都能继续同一份开发成果，而不是维护三套互相等待的开发进度。日常 exe 的验收与发布边界保持不变。

下表全部由 Codex 串行实施，不是对其他平台的派单表。本次接管先完成旧工作区核对与执行规则调整，表内尚未实现的功能不因此标成完成。

| 顺序 | Codex 要完成的工作 | 用户看到的结果 |
| --- | --- | --- |

## 11. 给后续会话的交接规则

### 每个阶段写进统一交接文档

1. **完整任务名和本轮可见结果**：例如“修复设置保存期间再次编辑丢失”，不是只有代号或“完善架构”。
2. **现场**：当时 main 的完整提交、实际修改目录/分支、未提交内容、数据环境和仍在运行的程序。使用隔离目录时说明原因与合回状态，不直接拿本文起点作为所有阶段的基线。
3. **演示入口**：实际存在的启动命令或程序完整路径、预期模型/数据、具体操作顺序、截图/录屏位置。若尚未创建就先写待创建，不声称已能体验。
4. **实现边界**：已经改过哪些文件、当前结论、尚未解决的问题和避免回归的约束。不得为做一个界面顺便升级全部依赖。
5. **检查清单**：具体行为测试、实际组件/真实Electron/有声/ZIP各验什么；未验项目明确写出。fixture行为不能标成真实平台或真实画面。
6. **继续位置**：已提交内容、未完成工作、下一步应读的文件与应做的验证。额度不足时保持现场并交接，不自动将任务转给别的平台。

用户不需要逐条审核这些技术字段；它们由 Codex 记录，供下一会话直接接着做。用户主要看目标、演示和需要选择的产品问题。不再为单人开发新增一套 assignment/progress/result 文件。

## 12. 计划如何更新

每个版本结束只更新本文对应阶段结论和CURRENT顶部进度，不再追加一份平行总路线。代码事实变了就改“当前状态”，历史证据保留日期和版本。新增想法先进入后续候选，不挤掉已承诺的当前目标。

以后如果实现顺序变化，说明用户会提前获得什么、哪些结果延后、依赖和风险是否变化。**用户应当始终知道正在等哪个可以操作的成果，而不是只知道Agent还在工作。**
