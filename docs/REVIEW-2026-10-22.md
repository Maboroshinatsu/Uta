## 已复现问题

### [P1: 切换会话没有完整隔离流式状态和回复缓冲]

位置：

- `app/src/renderer/services/agent-presentation-controller.ts:328`
- `app/src/renderer/services/runtime-command-controller.ts:61`、`:145`
- `app/src/renderer/stores/chat.ts:76`

复现顺序：

1. 当前 Qoder 会话 A 收到 `rp_reply`，`streaming=true`，`requestId=shared-id`，正文为“旧会话内容。”，尚未收到 done。
2. 收到绑定会话 B 的 `session_bind`。
3. 此时 `agentWorkingState=idle`，但 `isSpeaking=true`；原来的流式看门狗已被清掉，没有后续事件时不会自动复位。
4. B 用相同 requestId 发送“新会话内容。”并结束。
5. 真实聊天 store 和语音缓冲均产生“旧会话内容。新会话内容。”。

根因：`resetSessionTurnState()` 只清去重与部分 Agent 字段，没有清 `isSpeaking/isThinking`、未结束的聊天流和 `ReplySpeechTracker.buffers`。聊天流与语音缓冲只按 requestId 索引，缺少 host/session 归属。TTS 的 `beginTurn()` 只清去重，不取消旧音频或队列，这是代码检查结果，未在本轮实听复现。

修复建议：在可见宿主/会话切换时统一收尾旧流、取消旧语音与相关计时器、复位说话/思考标记；内部流键应包含宿主和会话，兼容 legacy 指令。不要直接清空全部历史消息来代替流归属修复。手动切宿主也需要进入相同复位入口，目前舞台没有订阅宿主切换来做该清理。

影响范围：RuntimeCommandController、AgentPresentationController、ReplySpeechTracker、chat store、舞台接线和 TTS 取消入口。需要保护正常同一会话增量拼接与最终回复去重。

### [P2: 宿主预设入口绕过工坊编辑锁]

位置：`app/src/renderer/composables/usePresetController.ts:321`、`:342`。

复现顺序：

1. 设置 `presetEditingLocked=true`，工坊当前 `ParamAngleX=7`。
2. 调用 `handlePresetTrigger()` 被正确拒绝。
3. 用运行时实际注入的入口 `triggerPresetOrGroup()` 触发参数为 20 的同一个预设。
4. 调用返回 true，slider 和下发给模型的控件层均变成 20。

根因：编辑锁只在 `handlePresetTrigger()` 中拦截；宿主指令、Agent 状态等实际走 `triggerPresetOrGroup()`，它直接调用 `applyPresetByEntry()`。所以用户编辑时可能被宿主抢走模型预览，即使编辑器内的步骤数据仍保留，也会造成预览与表单不一致。

修复建议：统一外部预设/情绪入口的编辑锁判定；工坊主动预览保留显式通道。需要同时检查 `handleControlAction()` 的预设分支，避免只补一个入口后仍有旁路。

影响范围：预设控制器及其宿主调用；重点验证编辑中收到 thinking/completed/set_preset 时不抢占，用户点击预览仍能工作，关闭面板后恢复正常状态驱动。

### [P2: 旧通知的说话计时器提前关闭新流式回复的口型]

位置：

- `app/src/renderer/composables/useCompanionDirector.ts:189`
- `app/src/renderer/services/runtime-command-controller.ts:137`、`:152`

复现顺序：

1. 短 `notify` 启动约 1200ms 的 `pulseBubbleSpeaking()`。
2. 到期前收到 `agent_state=streaming` 和第一段 `rp_reply`。
3. `rp_reply` 将 Agent 状态复位成 idle，随后设置 `isSpeaking=true`。
4. 原通知的计时器到期，看到状态不是 streaming，就写入 `isSpeaking=false`。
5. 真实 chat store 的消息仍为 `streaming=true`，但舞台说话标记已关。

影响：流式文本口型会提前闭合，后续分片到达又重新开启，可能表现为不连贯；这不是已经复现的真实 TTS 包络故障，音频口型还有独立的 `ttsSpeaking` 路径。

修复建议：通知脉冲与真实流式回复分别持有状态/令牌，或在流式开始时取消旧脉冲；不能用 `agentWorkingState` 代替真实流是否仍活动的判定。
