## 已确认的问题

### [P1: DSH 指定会话失效时，消息误投其他会话且报告原目标发送成功]

位置：`plugin/plugins/deepseek-harness/src/index.mjs:1272–1277`；`app/src/main/host-bridge.ts:178–183,528–529`。

DSH 原生消息桥先按请求的 `sessionId` 找 agent；找不到时继续使用全局活动会话或最后一个 root。主程序只检查 `ok/accepted`，忽略桥响应里的实际 `sessionId`，最后把请求的 ID 写回成功结果。因此，即使界面固定了目标且主进程没有选择其他会话，消息仍可能在插件层流向其他项目。

隔离复现使用生产插件 `apply()`、真实回环 HTTP 服务与生产 `sendHostMessage()`，仅替换宿主 agents 服务：请求 `session-A-missing`，agents 中只有 `session-B`；B 的 `followup()` 实际收到消息，主程序返回 `ok=true / accepted=true / sessionId=session-A-missing`。没有向真实宿主或真实账号发送消息。

影响：普通输入和调用同一发送桥的项目/日常待办都可能受影响；主进程发送前的 cwd 检查不能约束插件后续选择了别的 agent。

修复方向：有显式目标时必须精确查找，缺失就返回不可投递，禁止另选 agent；主程序也必须校验实际接收目标，不能把不一致回执显示为成功。回归应覆盖目标关闭、多个 root、固定旧会话和响应目标不一致。

### [P2: DSH 原生桥回执中断后，自动回退命令行可能重复投递]

位置：`app/src/main/host-bridge.ts:198–202,528–532`。

原生桥超时或任意请求错误均返回 `null`，调用方随即运行 headless CLI。这里没有区分“连接前失败”和“请求已被接收但成功回执丢失”，也没有跨通道的幂等消息标识。

隔离复现用真实 HTTP 服务收到完整请求后记录一次接收并主动断开 socket，生产发送桥随后确实启动了假的宿主 CLI，后者记录同一条输入并返回成功。结果是一次用户操作触发 **原生入口 1 次 + CLI 入口 1 次**。

这是生产发送桥的重投行为复现，第二入口使用假 CLI；没有证明真实 DSH 在所有情况下都会执行两次。真实 headless 可能因会话占用拒绝，或者在原会话已完成/退出后再次接收；无论哪种情况，都不能把第一次的投递结果当作确定失败。

修复方向：仅在可以证明尚未投递时自动换通道；请求提交后的断线/超时显示“投递结果未知”，避免静默重发，或设计宿主端可去重的稳定消息 ID 与结果查询。回归至少覆盖接收后断线和接收后超时。

证据：本机 `.tmp/review-20261031/host-boundary-probes.cjs` 与 `host-boundary-results.json`。脚本刻意断言当前缺陷存在，修复时须反转断言并纳入正式测试；本地文件包含隔离端点数据，不整目录提交。
