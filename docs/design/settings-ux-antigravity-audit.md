- sender 应按职责分别校验 settings 与 stage，不能同时要求 settings 请求通过只认可 stage 的旧 isRuntimeSender。新专用 preload 仅暴露白名单，保留 contextIsolation/sandbox；不要复制下方原文为未经审查的完整接口设计。

## 1. 审查意见逐项响应与事实修正

### 1.1 宿主反向文本桥与能力声明的统一
- **源码核实**：
  经复核 [app/src/main/host-bridge.ts](D:/Frankenstein/Uta/app/src/main/host-bridge.ts) 与 [app/src/renderer/components/DeskpetStage.vue](D:/Frankenstein/Uta/app/src/renderer/components/DeskpetStage.vue)，主进程确实存在针对多宿主的实际反向文本桥：
  1. **Codex**：通过 `buildCodexArgs` 调用 `codex.exe queue --thread <sessionId> --message <text>`，以 `acceptedOnly: true` 异步入队，回复通过既有 Hook 事件带回；
  2. **DeepSeek Harness**：支持通过 Native Bridge 端口直接注入，或回退至 `headless --session-id` 标准输入管道；
  3. **Claude Code / ZCode / OpenCode**：分别通过各 CLI 的 `--resume` / `--prompt` / `run --session` 反向发送。
- **事实纠偏**：
  首版报告仅根据 [hook-host.ts](D:/Frankenstein/Uta/app/src/renderer/services/adapters/hook-host.ts) 中渲染层适配器声明的 `sendInput: false`，便推断宿主不具备反向文本能力，属于**将渲染层声明缺陷误当作系统整体能力缺失**。
- **定稿方案**：
  - 核心问题定性为：**“渲染层适配器静态能力声明与主进程实际文本桥实现脱节，缺乏统一只读能力视图”**。
  - 界面呈现将四重事实完全解耦展示：
    1. **静态实现（Capability Implementation）**：底层是否具备 CLI/Native 驱动实现；
    2. **配置就绪（Configuration Readiness）**：可执行路径与依赖文件是否存在；
    3. **会话与忙碌状态（Session & Busy State）**：是否存在未超时的活动会话文件（`updatedAt` 处于 30 分钟窗口内），是否处于发送冷却期；
    4. **端到端验收状态（E2E Verified）**：以真实会话握手或测试结果为准，未经验证的平台明确标注“未验证”，绝不宣称全平台已测可用，亦绝不把开发平台的 CLI 派单指令当成桌宠产品的对话输入。

---

### 1.2 预设存储规范与 Profile 数据隔离约束
- **原则确立**：
  - **废止向模型根目录写入**：新方案**严格禁止**继续调用 [main/index.ts](D:/Frankenstein/Uta/app/src/main/index.ts) 中的 `saveModelPresetsToDisk` 向共享模型目录直接覆写 `deskpet-presets.json`。模型身旁的 `deskpet-presets.json` 仅作为出厂初始只读模板及历史数据源；
  - **Profile Canonical 存储**：用户的所有自定义预设、修改覆盖与常驻标记，必须作为各 Profile 专属数据落盘于 `environment.userData` 目录内（严禁在代码中硬编码任何绝对路径或 `%APPDATA%/uta`）；
  - **台账状态修正**：原报告功能归属表中的“模型同级目录”仅代表代码**现状存储**，新架构的**建议目标**统一变更为 `environment.userData/presets/<model-hash>.json`。
- **配置容灾与可恢复状态**：
  若检测到用户配置文件解析损坏或格式异常，**严禁使用出厂默认值静默覆盖原文件**。主进程必须将损坏文件重命名备份（如 `.corrupted.<timestamp>`），并在设置中心向用户发出明确告警，进入带有修复/重置选项的“可恢复状态”。

---

### 1.3 预设工坊编辑锁与动作调度修正
- **舍弃队列重放**：
  首版方案中提出的“工坊解锁后重放缓冲的外部 Agent 动作”被证实违背交互直觉——Agent 先前的情绪状态具有强时效性，解锁后补放已过期的表情只会干扰当前用户工作流。
- **采纳明确拒绝与阻断机制**：
  1. 工坊进入编辑态时持有带租约的排他锁：校验 `editorSessionId`、`modelId` 以及配置 `revision`，窗口意外崩溃时通过主进程心跳检测自动超时释放；
  2. 编辑锁持有期间，入站的**文本消息与工具审批交互照常进行**，但涉及模型的**外部姿态、情绪与动作指令直接拒绝**，并在宿主响应日志中明确回显拒绝原因（如 `pet_busy: preset_editing`）；
  3. **动作语义解耦**：工坊中的“保存预设”仅负责持久化数据，**不触发自动播放**；“预览分镜”与“应用动作”保持为独立显式按钮。

---

### 1.4 撤回无实测依据的性能断言
- **撤回内容**：
  撤回首版报告中关于“实测 IPC 小于 1ms”、“性能零损耗/内存零负担”以及“扩大透明窗口极重”等缺乏基准测试数据的定性表述。
- **修正为待测假设与性能预算**：
  - **工坊参数透传**：设定跨窗口预览 IPC 延迟预算上限为 `16ms (60fps)`，实际开销作为后续迁移任务的待测项；
  - **动画与渲染**：保留精简装饰性物理动画循环的建议，但客观承认 [SettingsPanel.vue](D:/Frankenstein/Uta/app/src/renderer/components/SettingsPanel.vue) 的 `stepHandfeel` 代码复杂度不能等同于实测性能卡顿，后续以实际 Chromium Profiler 帧耗时与 CPU 占用为准。

---

### 1.5 进程安全边界与 Preload 隔离重申
- **保留隔离**：
  纠正首版示例中的错误配置，主程序及新设置窗口**必须严格继承并保持** [main/index.ts](D:/Frankenstein/Uta/app/src/main/index.ts) 的安全底线：
  ```typescript
  contextIsolation: true,
  sandbox: true
  ```
- **专用 Preload 与白名单通道**：
  - 新增设置窗口专属的 Preload 脚本，仅暴露最小必需的配置读写与工坊调参 API；
  - 主进程 IPC 处理器实施严格的 `isRuntimeSender` 及 `sender.id === settingsWindow.webContents.id` 来源鉴权；
  - 主进程向各窗口广播配置变更事件时，**严禁广播明文 API Key 或无权限敏感字段**，渲染层仅接收 `hasApiKey: boolean`。

---

### 1.6 窗口拓扑收敛：确定双 OS 窗口架构与小屏适配
- **严格限制为双窗口**：
  系统默认仅保留 **2 个操作系统窗口**：
  1. **桌宠主窗口**（透明、穿透、贴边桌面伴侣）；
  2. **设置中心窗口**（标准操作系统外框独立大窗）。
  - **预设工坊不是第三个 OS 窗口**：工坊作为独立专用工作区内嵌于设置中心中；全系统**绝不加载第二份 Live2D 运行时、宿主桥或语音音频实例**，参数微调统一通过单向轻量 IPC 驱动主窗口舞台渲染。
- **小屏与 WorkArea 弹性夹取**：
  废除硬编码的 `minHeight` 限制（避免在低分辨率或高 DPI 缩放下将底部的“保存/取消”按钮推至屏幕可见区域之外）。窗口尺寸与弹性滚动容器根据操作系统 `screen.getDisplayMatching().workArea` 进行动态高度夹取与布局折叠。

---

### 1.7 平台与连接信息架构重构
- **合并连接总入口**：
  设置中心不再将宿主割裂为“Agent 工作型宿主”与“第三方适配器”两套独立入口，统一收拢为**「连接与会话 (Connections & Sessions)」**总表；
- **真实证据链展示**：
  - 废除以简单的“60 秒文件更新”假充“会话已绑定”的逻辑；
  - 环境检测无法探测到宿主安装时，诚实呈现为 `未验证`；
- **配置与交互纯粹化**：
  - UI 字段使用持久的专业静态标签，废止晦涩占位符；
  - 关闭 TTS 播报仅静默语音合成，文本摘要在气泡中继续呈现；
  - 配置修改不触发自动重连或静默落盘；
  - “测试草稿配置”使用内存瞬态执行，在用户未点击保存前绝不落地写入敏感存储文件；在底层未实现独立的试听 API 前，不以现有的常规语音合成冒充服务测试。

## 3. 实施前应确认的三项关键产品决定

在下一阶段正式拆解开发任务单（TASK）之前，建议项目主控与用户就以下三项产品层面的决策达成最终共识：

1. **预设数据从“模型旁车”向“用户 Profile 专属数据”的迁移过渡策略**：
   - *待决项*：对于用户先前在模型目录下创建的 `deskpet-presets.json`，是在首次加载时**只读导入并自动镜像复制到 `environment.userData`**，还是允许用户在界面中手动点击“从模型目录导入/导出预设”？
   - *建议倾向*：首次检测到用户目录无预设时静默读取旧文件作为基准生成 Canonical 配置，不再向原模型目录反向写盘，确保模型根目录的只读资产属性。

2. **工坊调参时双窗口在屏幕上的空间协同排布**：
   - *待决项*：由于桌宠主窗口与独立设置中心为两个独立的 OS 窗口，在用户点击“进入工坊”时，系统是否需要提供“智能吸附分屏”（例如将设置窗口自动摆放在桌宠左侧或右侧），以保障用户在不同尺寸屏幕下调节滑块时均能无遮挡看到桌宠舞台？
   - *建议倾向*：提供“智能避让/并排贴靠”辅助功能，但不强制锁定窗口物理位置，允许用户在多显示器环境下自由跨屏拖拽排布。

3. **无官方反向文本注入通道平台的界面降级引导**：
   - *待决项*：针对当前在 [host-bridge.ts](D:/Frankenstein/Uta/app/src/main/host-bridge.ts) 中明确返回 `unsupported` 的平台（如 Qoder、Antigravity 等未开放官方 CLI/API 外部文本注入的宿主），桌宠输入框在用户尝试回车时应如何交互？
   - *建议倾向*：当活动宿主无文本注入能力时，输入框上方提供明确静态提示卡：“当前平台不支持外部文本注入，请在对应宿主中直接输入”，输入内容支持一键“复制到剪贴板”，避免产生输入丢失的挫败感。
