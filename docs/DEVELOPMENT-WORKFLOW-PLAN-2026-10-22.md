# Uta 四平台开发协作与环境治理方案

日期：2026-10-22（Asia/Shanghai）

受众：维护者及 Codex、Qoder、Antigravity 开发会话，DeepSeek Harness 兼容性测试会话
状态：用户已批准分阶段实施。用户补充确认：已验收的日常版本必须是 ZIP 打包后解压、直接启动 Uta.exe 的版本，运行目录独立于源码。实施进度以 `workflow/CURRENT.md` 为准。下文路径、环境变量和脚本除明确标为现有外，均是设计，不能当作已交付。

## 1. 要达到的工作方式

用户只向 Codex 提需求、确认产品方向和查看验收结果。Codex 负责拆任务、确定接口、分配开发区、审查交付、决定合并及发布；Qoder、Antigravity 在各自任务区提交开发成果。DeepSeek Harness 只验证 Uta 在 DSH 上能否使用，不参与日常开发。用户仍可随时改变方向、否决合并或指定平台。

保持一份日常使用的 Uta 设置。开发副本的设置有意隔离，但来源、名称、端点和版本必须可见；测试结果不能通过碰巧连接日常实例来获得。

开发环境分为三层：日常使用、集成验收、任务开发。代码隔离、运行数据隔离、平台插件配置隔离分别建立，不能相互替代。

## 2. 已查明的混乱来源

| 现状 | 影响 | 治理方向 |
| --- | --- | --- |
| Git 只有 `D:\Frankenstein\Uta` 一个 worktree，分支为 main | 多个平台在相同文件、索引和构建目录中写入 | 一任务一分支、一任务一 worktree |
| 未配置 Git remote，仓库未见 CI 配置 | 暂无远端合并约束或自动验收 | 先落地本机集成检查，不以 PR 为前提 |
| 主进程把 userData 固定为 `%APPDATA%\uta` | 多个源码目录仍可能共用数据与单实例锁 | 显式 profile 和独立 userData |
| 开发模式加载 Vite 地址，本地构建加载 file 页面 | 同一 userData 内也有不同页面 origin 的 localStorage | 持久设置由主进程统一管理，脱离页面地址 |
| 宿主选择、模型选择、预设等在 localStorage；窗口与语音等另存文件 | 看起来像同一个应用，却得到不同设置 | 按用途分层保存，并提供明确导入和诊断 |
| start-uta.bat 直接执行 app/out 对应的 Electron 入口，不构建 | 源码已改，运行的仍可能是旧构建 | 日常入口运行固定发布产物；开发入口展示构建来源 |
| 客户端依次尝试覆盖路径、Uta 目录及旧版目录 | 测试端点缺失时可能连接另一份实例 | 显式端点严格匹配，开发环境禁止隐式回退 |
| hook 的部分日志、会话和去重文件写死在 `%APPDATA%\uta\hooks` | 只改端点仍不能隔离平台事件 | 所有运行文件通过同一 profile 解析器定位 |
| 插件源码、dist、本地市场和四个平台安装缓存并存 | 修改源码并不代表平台执行新插件 | 集中构建、明确安装记录、从实际平台验收 |
| 旧规划、历史交接和当前现场并存 | 新会话容易把历史状态当当前事实 | 一份当前入口，历史文档保留为记录 |

## 3. 职责、权限与派单

| 角色 | 负责内容 | 交付方式 |
| --- | --- | --- |
| 用户 | 产品目标、交互取舍、方向调整 | 对 Codex 提需求与反馈 |
| Codex 主控会话 | 架构与任务契约、排期、审查、验收、合并、日常环境与安装管理 | 任务台账、审查记录、集成提交、安装清单 |
| Codex 自己的实现会话 | 需要 Codex 实现的具体任务 | 同样使用任务区并交付提交 |
| Qoder / Antigravity 开发执行会话 | 完成明确开发任务、局部验证、报告风险 | 任务分支提交和验收材料 |
| DeepSeek Harness 测试会话 | 只验证 Uta 在 DSH 上的安装、连接、状态、回复、气泡、动作及审批兼容性 | 复现步骤、测试结果和缺陷报告；不实现业务修复 |

不按平台名称假定能力强弱。初期可以让 Qoder 承担范围明确的模块修复，Antigravity 承担渲染或界面任务；实际开发分配根据已有上下文、接口支持和交付质量调整。DSH 的角色由用户明确限定为本宿主兼容性测试，不分配共享 SDK 实现、日常功能开发或其他平台验收。DSH 测出的问题由 Codex 归因并分派修复。

工作会话不直接修改 main、不自行合并、不修改其他任务区、不全局安装插件、不覆盖日常数据。公共接口、锁文件、主进程入口、共享 SDK、设置模型等冲突高的文件，同一时间只分配给一个实现任务；相关任务依赖其接口先行交付。

**这些是协作规则，不是安全沙箱。** Git worktree 共享 Git 对象、分支引用和本机用户权限，无法阻止任意命令访问其他目录。第一阶段用规则、任务范围检查和人工审查落实；若需技术上强制禁止越界，应另设 Windows 用户/受限执行器/容器，不能宣称 worktree 已做到权限隔离。不要用互相覆盖 ACL 或递归调整完整性级别的方式模拟隔离。

## 4. 目录与 Git 布局

建议在同一磁盘建立如下布局，工作区继续位于 Frankenstein 通用规范覆盖范围内：

```text
D:\Frankenstein\Uta\                       主仓库 / main，Codex 集成入口
D:\Frankenstein\Uta-Workspace\
  tasks\<任务名称>-<平台>\                  一任务一 Git worktree
  integration\<验收批次>\                  集成候选 worktree
  runtime\profiles\<任务名称>\             开发设置、日志、端点、缓存
  runtime\profiles\integration\            集成验收数据
  artifacts\<提交SHA>-<构建编号>\           独立构建产物和来源清单
  operations\                              本机分配表、进程与安装记录
  backups\                                 受控备份，不入 Git
```

主工作区存放源码和版本化任务契约；本机 PID、端点令牌、绝对安装路径、临时日志放 operations/runtime，不写进 Git。日常使用数据继续保留在 `%APPDATA%\uta`，第一阶段不搬家。

分支命名示例：`task/qoder/session-reset`、`task/harness/endpoint-isolation`。一个工作分支同一时间只有一个写入会话；任务结束后可复用平台会话，但不能让两个任务共用一个分支。

各 worktree 独立安装依赖、生成 out/dist 和 TypeScript 缓存。允许共享包管理器下载缓存，不通过目录链接共享 node_modules 或 out/dist，避免一个平台构建时覆盖另一个平台的产物。模型测试使用少量测试夹具；大型自有模型可以显式只读挂载，相关测试不得写回源模型。

## 5. 运行数据与设置的目标结构

### 5.1 三种运行环境

| 环境 | 设置目录 | 默认用途 | 谁能升级 |
| --- | --- | --- | --- |
| 日常 stable | 现有 `%APPDATA%\uta` | 用户持续使用、保留正式设置 | Codex 在验收后统一升级 |
| 集成 integration | 独立 integration profile | 合并候选及四宿主桌面回归 | Codex |
| 任务 task | 每任务独立 profile | 实现调试、自动测试、平台局部验收 | 对应执行会话 |

拟增加 `UTA_PROFILE`、`UTA_USER_DATA_DIR` 和统一路径解析。初始化必须在单实例锁、Electron session 与窗口建立之前完成。单实例锁按 profile 区分；同一 profile 只允许一个实例。测试 profile 默认不注册全局快捷键、不自动迁移旧模型、不访问真实麦克风、不使用日常云语音凭据。

运行标识应至少展示：环境名称、profile、userData、源码目录、提交 SHA、构建时间、页面加载模式、当前宿主/会话、端点状态。普通用户界面给出简短名称，技术详情通过诊断面板或脱敏导出提供。

### 5.2 一份设置的含义

长期持久设置由主进程提供版本化读写接口，渲染层通过受限 IPC 访问。先迁宿主选择、模型选择和预设，再迁其他持久偏好；临时界面状态可保留在浏览器存储中。

建议每个 profile 内分开存放：非敏感 settings、模型与预设、历史聊天、临时 runtime（端点/锁/会话/去重）、日志和缓存。令牌与密钥不放进共享任务文档，也不随普通 profile 导出。保留现有 safeStorage 等敏感配置保护；复制文件不能被视为跨用户可解密迁移。

分离 userData 只能解决不同环境相互覆盖，不能消除同一环境内 Vite 与 file 页面 origin 分裂，因此持久设置迁移是单独的必要工作。暂不同时更换整个页面协议，降低改动范围。

### 5.3 无损迁移

1. 在短暂关闭相关实例后备份现有 Uta 数据，并保留旧版目录；不删除 LevelDB、预设或旧应用数据。
2. 通过各原页面自己的设置导出机制读取各 origin 数据，不在 Electron 打开时直接改 LevelDB。开发页面需要能识别其原地址；无法读取的来源列为待恢复，不声称已合并。
3. 生成来源清单和差异报告。默认以用户现在常用的 start-uta.bat 本地构建页面作为日常设置候选；同名预设与模型配置冲突展示差异，不能用最新修改时间静默覆盖。
4. 主进程存储初始化时迁入选定来源，记录 schemaVersion、迁移来源和完成标记。渲染层等设置加载完成后再启动宿主/模型，避免默认值抢先覆盖。
5. 验证宿主、模型、工坊预设、窗口、语音开关与重启持久性。失败时回退到旧数据和旧构建，不能只回退代码却继续使用不兼容新数据。
6. 开发 profile 从脱敏种子或指定快照创建，只作为副本；不自动双向同步日常设置。

## 6. 端点、hooks 和四平台插件隔离

一个 profile 对应自己的端点、会话记录、发言抑制标记、去重文件和审批请求。所有插件及主进程共用路径解析规则，不能只把 runtime-endpoint.json 改掉而保留硬编码 hooks 目录。

拟增加 `UTA_RUNTIME_DIR`（目录）并保留 `UTA_ENDPOINT_FILE`（精确文件）兼容入口。明确给出路径时只允许访问该目标，缺失、过期、不可用都失败；不能转而操作日常实例。旧 `DESKPET_ENDPOINT_FILE` 的优先级与冲突行为需明确并测试，两者冲突时应报错。

旧版目录回退只用于未显式选择环境的兼容入口；开发与集成模式禁用。协议能力缓存需绑定实例身份，而不只是相同端口；端口、token 或 instanceId 改变时重新握手。

端点发布与诊断建议增加 instanceId、profile、PID、启动时间、协议版本、构建来源。文件先原子写入，启动发布失败要关闭已创建的监听服务并明确记录错误，避免“端口在但配对文件过期”。客户端失败后可重读同一目标并重试一次无副作用查询；通知、回复、动作和审批不得在没有请求去重保证时盲目重放。健康检查不回显 token。

插件安装分为正式槽与测试槽。任务区只生成测试产物；Codex 统一把验收版本安装到平台真实配置。已安装插件的缓存、市场目录和源码不是同一物，安装记录必须包含平台、配置作用域、源提交、版本、产物校验值、实际安装位置与验收结果。

各平台能否对单会话传环境变量、使用项目级 MCP/hooks、使用独立用户配置，必须分别验证。可用则为任务会话指定 profile；不可用则使用独立平台配置目录或串行预约测试槽。不要为了隔离 Uta 而整体伪造 APPDATA，导致宿主登录和其他应用配置丢失。

## 7. 派单与交付协议

### 7.1 先可追踪，再自动化

Uta 的“宿主状态桥”是产品功能，开发任务调度是另一套系统。当前代码中的宿主反向消息只覆盖部分平台；Qoder、Antigravity 的可靠派单接口仍需验证，不能把 MCP 角色工具当成能调度其他 Agent 的证据。

第一阶段：Codex 写好任务单及平台启动说明，用户仅负责在对应平台打开指定任务目录、投递一次任务单。Codex 从提交与结果文件收取交付，用户无需在平台间整理上下文。开发派单对象是 Qoder 与 Antigravity；DSH 只在需要测试 DSH 兼容性时启动测试会话，不长期占用开发执行席位。

第二阶段：对每个平台验证 CLI/会话 API 后接入薄调度适配器，提供启动、发消息、取状态、取消、收交付，记录任务与真实会话 ID。优先文件交付，即使消息丢失也能恢复。禁止模拟点击自动点批准、复用不明的最近会话或绕过平台权限。

消息派发只向已登记的执行会话发送具体任务；方向、目录或基础提交变更时重发任务契约。当前规划阶段尚未调用任何平台发任务，也未声称四个平台已能自动互控。

### 7.2 每张任务单必须包含

- 完整名称、目标与用户可见验收行为。
- owner 平台、分支、worktree、base SHA、依赖任务与当前状态。
- 允许修改的文件/模块；公共接口契约；不得改动的资源与全局配置。
- 测试 profile、端点目标、启动与验证命令、是否需要真实模型/人工观察。
- 明确完成条件、必须留存的证据、已知风险与待确认点。
- 交付 head SHA、修改摘要、测试命令和结果、日志位置、启动进程与待清理资源。

推荐版本化文件：`docs/workflow/tasks/<任务名称>.md` 与 `docs/workflow/results/<任务名称>.md`。Codex 写任务单，执行会话只写自己的交付文件，避免多 Agent 同时改一张总表。运行状态和资源租用表放仓库外 operations，由 Codex 或调度器单写。

任务状态：待安排 → 已派发 → 实现中 → 待审查 → 待集成 → 已合并 → 已验收；另设阻塞、退回和取消。完成声明只是进入待审查，不能自动变成已合并。

执行会话开工先报告 pwd、branch、base SHA、工作区是否干净与 profile；发现目录或基线不符就停止依赖操作并报告。交付前提交自己的变更，只清理自己的进程；不得暂存其他人的文件，也不写跨任务总交接。

## 8. Codex 审查和合并

1. 接收确定的 head SHA，确认从任务 base 派生，检查工作区与范围；未提交改动不能算交付。
2. 审查实际 diff，核查接口、数据迁移、越界文件和依赖。执行会话报告通过不能替代审查。
3. 从当前 main 创建集成候选，按依赖顺序应用该任务；同一时刻只有一个合并操作者。不让各执行会话自行 rebase/merge main。
4. 在集成候选上运行与变更相称的检查；有新失败或集成冲突时退回任务修正，实质修改后重新验证。
5. 对确定的候选 head 与最终树做记录；通过后才把候选合入 main。日常构建来源必须对应已验收提交。
6. 更新任务结果与当前交接入口；安装/发布是独立步骤，记录真实安装状态。需要用户确认的产品方向单独提出，常规已授权任务的合并由 Codex 决定。

初期优先保留语义清楚的任务提交，通过串行合并维护历史；不并存一套 merge、一套 cherry-pick 的隐式流程。确需挑选独立修复时记录来源，避免随后重复引入。

自动检查层次：纯文档不跑全套；逻辑变更跑对应回归与类型检查；涉及主进程/渲染或公共 SDK 时跑 app/test:plugin 相关集合及构建；发布候选完成四平台桌面冒烟。当前已有 `npm run typecheck`、`npm test`、`npm run test:plugin`、`npm run build`、`npm run plugin:build`，由任务范围选用，数量以当次日志为准。

真实验收要分别证明：平台发现工具、服务握手、桥接受、当前会话归属正确、气泡与模型实际响应；必要时验证用户批准/拒绝/超时仍由宿主正确处理。HTTP 成功和工具字符串都不能单独证明渲染成功。

## 9. 日常启动、构建与发布

已确认日常形式：ZIP 包解压后直接运行 Uta.exe，目录独立于源码与 app/out。保留 start-uta.bat 作为可选快捷入口时，也只能指向 Codex 提升到稳定槽的已验收 exe。启动不自动更新源码、不临时构建、不重新安装插件；应能够说明自己运行哪次发布。设置仍保留在用户数据目录，不因“解压运行”自动改成 exe 同目录存储。

开发入口必须显式选择 profile，启动前打印目录、提交、profile 与目标端点。集成入口只运行候选构建。推荐未来新增集中环境管理脚本，提供 new-task、start、status、doctor、verify、promote、cleanup 等操作，而不是每个平台各写一套批处理；这些命令目前尚不存在。

发布清单包含源码 SHA、dirty 状态、构建工具版本、产物校验、四平台插件版本、验收记录与回退版本。修改源码和生成 out 不等于发布完成。日常稳定槽保留上一版；涉及数据迁移时同时保留对应数据快照。

## 10. 第一批实施顺序与建议分工

| 顺序 | 事项完整名称 | 建议执行者 | 交付与验收 |
| --- | --- | --- | --- |
| 1 | 当前数据盘点与协作入口建立 | Codex | 数据来源清单、备份、当前状态入口、任务模板，保全现有改动 |
| 2 | profile 路径契约与主进程环境隔离 | Codex | 路径接口、独立 userData/锁/快捷键策略；同机运行两测试环境互不覆盖 |
| 3 | 共享 SDK 端点与 hooks 文件严格隔离 | Codex 实现或分配给 Qoder | 基于顺序 2 接口实现；断开测试端点不能命中日常实例；四插件回归；DSH 仅验证其宿主链路 |
| 4 | 持久设置统一与旧来源迁移 | Qoder 执行任务 | 主进程设置服务、明确冲突处理、备份回退；dev/本地构建读取同一 profile 设置 |
| 5 | 运行身份与诊断界面 | Antigravity 执行任务 | 基于已定 IPC 接口展示环境/构建/端点；普通模式保持简洁 |
| 6 | 任务 worktree、进程与安装记录工具 | Codex | 新建/检查/关闭任务区，范围检查，集中验收与安装 |
| 7 | 开发平台调度与 DSH 测试入口试点 | Codex 按用途逐项验证 | Qoder/Antigravity 验证开发派单；DSH 只验证测试任务的启动和结果收取；未支持则继续人工启动 |
| 8 | 独立稳定产物与统一日常入口 | Codex | 从验收提交构建发布，插件安装登记，重启和上一版回退 |

顺序不是八项全串行：先定好路径与 IPC 契约后，顺序 3/4/5 可以在不同文件范围并行；主进程入口和共享协议变动由 Codex 协调。先用一个小任务试跑交付合并，再扩大并行量；不为了同时启用四个平台强行拆出互相依赖的任务。

现有会话重置、工坊编辑锁和口型计时器问题继续留在问题台账，环境治理稳定后作为第一批功能修复候选；不在这次流程改造中悄悄夹带。

## 11. 完成标准与恢复方式

- 日常启动始终进入同一稳定设置，显示确定版本；修改开发区不改变日常实例。
- 两个以上任务区可独立构建运行，设置/端点/hooks/预设/构建目录不串写；显式测试端点失效时不回退日常实例。
- 四平台每次交付都能追溯到任务、base/head SHA、profile 和验收证据；Codex 能独立收取并拒绝不合格交付。
- 工作会话不安装全局插件，main 只接收验收完成的变更；日常环境与测试实例不会抢占全局快捷键或声音。
- 新开 Codex 主控会话只需读取项目 AGENTS、当前状态入口与未完成任务即可继续；平台聊天历史不是唯一事实来源。
- 任务失败保留分支与交付日志，候选失败不提升 main；数据迁移失败能恢复旧应用和旧数据，未批准清理前不删除历史目录。

## 12. 下一步决策

本方案建议采用：**Codex 主控 + 一任务一 worktree + 一环境一 profile + 本机串行集成 + 先任务单后自动派单**。用户确认方案后从顺序 1/2 开始，不先投入完整调度平台，也不要求立即迁移到远程仓库。

参考：OpenAI 官方的 [Codex worktree 使用建议](https://developers.openai.com/blog/mastering-codex-remote-for-engineering)支持以独立 worktree 隔离代码并等待环境准备完成；本文的四平台职责、profile、派单与验收规范是针对 Uta 当前代码提出的设计，并非平台已经提供的完整跨产品编排能力。
