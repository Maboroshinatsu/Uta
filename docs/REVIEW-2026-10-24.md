# Uta 全面代码与使用体验审查

审查于 2026-10-24 开始，2026-10-25 完成。读者：维护者与后续开发会话。

审查基线：`D:/Frankenstein/Uta`，`main`，`049220026a838eb879f276a126831e7525524f13`。这是当前源码的横向审查，不仅审查最近一次 diff；下述问题不统一归因于最近的功能提交。

## 结论

发现 **18 项可行动问题：4 项 P1、13 项 P2、1 项 P3**。16 个隔离探针支持其中 16 项问题；另外两项是宿主路径硬编码和用户文档过时。探针加载真实生产模块或抽取真实函数，以模拟 I/O、播放器、窗口和计时器控制触发条件；它们不是人工实听、真实桌面画面或完整宿主验收。

优先处理密钥归属与重定向、跨窗口宿主切换和随包静态立绘。现有应用/插件测试、类型检查与构建全部通过，说明目前测试存在跨模块覆盖缺口，不能以套件通过推断这些路径可用。

本轮没有修改业务代码，没有更新插件安装、ZIP、日常 exe 或正式数据。新增审查文档和临时复现材料；更新统一交接入口。

## 高优先级问题

### 1. [P1: 独立设置切换宿主没有同步到桌宠主窗口]

- 位置：`app/src/renderer/services/adapters/active.ts:140-165`；`app/src/renderer/settings-window/domains/ConnectionsDomain.vue:194-198`；`app/src/renderer/components/DeskpetStage.vue:838`。
- 触发：桌宠正在使用 Codex，在独立设置中选择 Harness，或选择“独立运行”。
- 结果：设置窗口的模块内 `active` 被替换，localStorage 也已保存新值；桌宠窗口自己的 `active` 没有收到通知，继续接收旧平台事件、向旧平台发送输入。关闭再打开设置仍可能显示新平台，进一步掩盖真实状态。
- 证据：两个独立模块实例共享同一存储；切换后设置实例的 `getActiveHostId()` 为 Harness，桌宠实例读到的偏好也是 Harness，但实际宿主仍是 Codex。现有 storage 监听只覆盖模型与预设等字段，没有宿主切换同步。
- 建议：由桌宠/主进程持有唯一宿主绑定；设置发送切换命令并等实际切换回执。重连和“独立运行”也走同一路径。覆盖双窗口切换、旧请求迟到、重启保留。

### 2. [P1: 打包版随附静态立绘全部被资源协议拒绝]

- 位置：`app/src/main/model-path-safety.ts:10-25`；`app/src/main/index.ts:1356-1367`；`app/src/renderer/public/models/sample_static/deskpet-images.json:5-13`。
- 触发：在打包版中切换到“示例立绘·团子”，或将 SVG 立绘放进用户模型目录。
- 结果：清单可以读取，但所有图片是 SVG；`MODEL_ASSET_EXTENSIONS` 没有 `.svg`，`uta://models/...svg` 被拒绝并返回 404。角色会空白，组件却已把清单加载当作 `modelLoaded=true`。源码内置资源走 Vite 时可能正常，因此开发态容易漏掉。
- 证据：对随附清单引用的全部七个实际存在的 SVG 调用生产 `resolveContainedModelFile()`，全部返回 null。
- 建议：统一立绘支持格式与协议白名单，可将随附图片转换为已支持的位图；若开放 SVG，应保留安全限制。首张图片实际可显示后才报告模型就绪。验证解压 exe 与用户模型路径。

### 3. [P1: 云端 TTS 更换接口域名会继续使用上一家密钥]

- 位置：`app/src/main/tts-cloud.ts:139-146`；`app/src/renderer/components/TtsSettingsSection.vue:319-345`。
- 触发：已经保存 OpenAI 兼容服务 A 的密钥，只将“接口地址”改为另一个服务 B，backend 仍为 `openai`。
- 结果：自动保存后仍保留 A 的密钥；下一次试听/播报把它发到 B。用户没有为 B 明确保存密钥也会发生。当前逻辑仅比较 backend，未比较 endpoint origin；STT 已有 origin 归属检查，但 TTS 没有。
- 证据：用两个 `.invalid` 域名与合成测试密钥调用生产 `mergeCloudTtsConfig()`，跨域后密钥保持不变。没有发送真实密钥。
- 建议：密钥归属至少绑定 backend 与 origin。来源变化时清除旧归属并要求为新服务显式保存；普通地址自动保存不得自动转移密钥。

### 4. [P1: 云端 TTS 跨域重定向继续携带认证头]

- 位置：`app/src/main/tts-cloud.ts:202-208`。
- 触发：已配置的合成接口返回指向另一个 origin 的 30x 响应，例如跳到音频 CDN、代理或其他域名。
- 结果：递归下载直接复用原 headers，`Authorization`、`api-key` 或 `api_token` 会跟到新地址；HTTPS 跳到 HTTP 也没有限制。该问题不依赖用户手动换接口。
- 证据：模拟 HTTPS 服务从 A 重定向到 B；生产合成函数发往 B 的请求仍带原 `Authorization`。全部传输为桩，未访问外网。
- 建议：跨 origin 删除认证信息、禁止携带凭据的 HTTPS 降级；按状态码处理重定向方法。覆盖三类认证头与多次跳转。

## 功能、可靠性与体验问题

### 5. [P2: 打开独立设置会把外部适配器偏好重置为独立运行]

- 位置：`app/src/main/index.ts:1531-1532`；`app/src/renderer/main.ts:40`；`app/src/renderer/services/adapters/plugin-loader.ts:103-104`；`app/src/renderer/services/adapters/active.ts:61-67`。
- 触发：用户当前选中了外部适配器，然后打开完整设置。
- 结果：`list-adapter-plugins` 仅允许桌宠 sender，独立设置只能得到空数组。设置窗口未注册外部适配器，随后把合法但未知的已选 ID 写成 `standalone`。插件消失且偏好被永久改写，下一次重启也受影响。
- 证据：生产 IPC handler 拒绝设置 sender，接着运行真实 loader 与偏好管理器，偏好从测试外部插件 ID 变成 `standalone`。
- 建议：让经过主 frame/页面验证的设置窗口读取插件清单；读取失败与“确实不存在”分开处理，不在读取失败时覆写偏好。

### 6. [P2: HTTP 适配器与页面 CSP 冲突且发送失败没有可见回执]

- 位置：`app/src/renderer/index.html:7`；`app/src/renderer/services/adapters/plugin-http.ts:58-60,80-87,116-138`；`app/src/renderer/services/adapters/builtin-plugin-manifests.ts:39-45,80-86`。
- 触发：选择 MaiBot、AstrBot 或一个声明式 HTTP 外部适配器，检测健康或发送文本。
- 结果：适配器在 renderer 中 fetch `http://127.0.0.1:8524/8526` 等地址，但 `connect-src` 仅允许 self、uta 和指定 ws，未允许这些 HTTP origin。静态契约表明这些请求会被 CSP 拦截。发送函数还会立即返回 true，稍后的拒绝仅写控制台；输入框已关闭，用户看不到投递失败。
- 证据：CSP 与生产请求地址静态核对；另用拒绝请求的 fetch 桩运行生产适配器，`sendUserText()` 仍返回 true。**本轮未用真实 Electron 抓取 CSP violation 或 HTTP 请求，不能把此项写成实机已测。**
- 建议：为声明式适配器提供受限的主进程代理，或明确、安全地配置可用连接范围；把投递结果改为可等待的回执，失败保留待发送文本并提供重试。不要简单放开所有网络权限。

### 7. [P2: 语音配置读取失败被当作首次使用并可被自动保存覆盖]

- 位置：`app/src/main/index.ts:1664-1683,1697-1711,1720-1739,1752-1770`；`app/src/renderer/components/TtsSettingsSection.vue:373-385`。
- 触发：`tts-cloud.json` / `stt.json` 损坏、暂时不可读，或原加密密钥解密失败，之后打开页面或修改普通服务字段。
- 结果：主进程吞掉错误返回默认配置/空密钥；renderer 无法区分“没有配置”和“读取失败”。后续写入可能覆盖原文件、丢掉服务配置或加密密钥。两份服务文件还直接 `writeFileSync`，缺少临时文件原子替换与备份，写入中断更容易进入这条链。
- 证据：让生产 TTS 读取函数遇到 EACCES，再执行普通字段合并和保存，写出的 `encryptedApiKey` 为空。STT 的同形读取/写入路径为静态核对，未另作磁盘故障注入。
- 建议：读取结果区分缺失、损坏、I/O 错误和解密失败；异常时保留原件并阻止覆盖，提供重新读取。普通字段保存保留不可解密的原密文，采用原子写与有效备份。

### 8. [P2: 正常设置保存会降级覆盖启动后被外部更新的文件]

- 位置：`app/src/main/settings-store/index.ts:270-288`；`app/src/main/settings-store/atomic-writer.ts:254-262`。
- 触发：应用读入有效 schema 1 设置后，主文件被外部工具/较新版本改为未来 schema，再在旧实例保存一次偏好。
- 结果：patch 只检查内存 revision，没有重验当前磁盘文件；会把未来 schema 写回 schema 1。原内容暂时进入 backup，但下一次保存会继续轮换覆盖。若磁盘主文件已损坏，也会把损坏内容覆盖到原有效 backup。
- 证据：真实临时文件、真实 SettingsStore：启动后将文件改为 schema 999，patch 返回成功，主文件变回 schema 1。现有“启动后外部升级”测试覆盖恢复入口，没有覆盖 ready 状态下的普通 patch。
- 建议：提交前检查磁盘 schema 与预期文件身份/版本；发现较新、损坏或外部变更时拒绝写入并提示重新读取，备份只接受已验证的有效旧文档。

### 9. [P2: 麦克风获取成功后初始化失败会遗留录音流]

- 位置：`app/src/renderer/components/DeskpetStage.vue:954-995`，尤其 `963-985`。
- 触发：`getUserMedia()` 已返回流，随后 AudioContext 创建/resume、节点创建或 connect 失败。
- 结果：`voiceStream` 到所有初始化完成后才赋值，catch 中的 `releaseVoiceCapture()` 看不到局部 stream，不能 stop tracks。界面显示录音失败，但麦克风资源可能仍被占用。快速重复点击还缺少“正在申请权限/初始化”的互斥状态，可能并发创建流。
- 证据：执行真实 `startVoiceInput()` 与 `releaseVoiceCapture()`，模拟音频上下文创建失败，已取得流的 track.stop 没有调用。并发启动为同一路径的代码检查结论，未真实申请麦克风。
- 建议：资源获得后立即登记，使用 try/finally 清理所有部分初始化资源；增加 starting 状态与卸载令牌，忽略并释放迟到的申请结果。

### 10. [P2: 开发与候选 profile 被无条件禁止使用麦克风]

- 位置：`app/src/main/index.ts:1411-1415`；`app/scripts/start-candidate.bat:3-6`。
- 触发：按项目建议启动独立开发实例，或双击候选包的 `Try-Uta.bat`，开启语音输入并点击麦克风。
- 结果：两个权限 handler 都要求 `environment.isStable`，因此自己的主窗口也必然被拒绝。独立数据环境中的 STT 无法使用，也无法在不触碰日常数据的前提下完成麦克风验收。界面仍提供完整开启入口。
- 证据：运行真实两个权限 handler，以非 stable profile 和合法主窗口请求 media，两个结果均为 false；没有实际请求系统麦克风。
- 建议：按可信窗口、主 frame、媒体类型与明确用户操作授权，不把数据 profile 是否日常作为唯一开关。若产品有意禁用，应在对应环境明确禁用入口并说明。

### 11. [P2: Runtime 投递失败的事件仍进入去重缓存导致重试假成功]

- 位置：`app/src/main/runtime-bridge.ts:398-410,458-463`；`app/src/main/runtime-sessions.ts:40-68`。
- 触发：窗口尚未 ready 或正在重载，带 eventId/seq 的命令第一次投递失败；窗口恢复后客户端重试同一事件。
- 结果：第一次虽返回 503，eventId/seq 已被 `sessions.accept()` 消耗。重试直接返回 `accepted=true, duplicate=true`，不再调用 sink，用户永远看不到这条消息/动作。
- 证据：自建临时 HTTP bridge，第一次 sink 返回 false；重试返回 duplicate/accepted，sink 总调用数仍为 1。端点已关闭、临时配对文件已删除。
- 建议：分离“接收/校验”和“成功投递”的去重提交；失败时允许重试，并保留并发重复请求的互斥。

### 12. [P2: 日常 HTTP/云端播报缺少播放阶段超时会卡住整个队列]

- 位置：`app/src/renderer/services/tts.ts:260-330,399-460`。
- 触发：合成已成功，但 Audio 元素停滞、永远不进入 playing，或不再派发 ended/error/pause。
- 结果：`speakHttp()` 永久等待，controller 的 running 一直为 true，后续播报只会排队。传入 timeoutMs 只影响合成请求，不覆盖播放；设置试听已有独立播放超时，日常队列没有。
- 证据：模拟播放停滞的 Audio，连续提交两条不同回复，只创建一个播放器，播放路径没有注册任何 watchdog。
- 建议：播放过程使用有上限的 watchdog，超时停止、释放 URL、复位口型并允许队列继续；监听取消与页面卸载。

### 13. [P2: 模型目录含井号或百分号时扫描可见但无法加载]

- 位置：`app/src/main/index.ts:229-232,245-252,1359-1360`。
- 触发：模型位于合法 Windows 目录 `Avatar#2`，或目录名包含看起来像 URL 编码的百分号序列。
- 结果：扫描直接把文件路径拼成 URL，未逐段编码。井号后内容成为 fragment，协议收到的路径被截短；百分号可能被额外解码或导致 URIError。列表里存在的模型，选中后却加载失败。
- 证据：创建临时 `Avatar#2/test.model3.json`，生产扫描返回 `uta://models/Avatar#2/test.model3.json`，URL pathname 实际只有 `/Avatar`。百分号相关后果是代码路径推导，未单列文件复现。
- 建议：构造资源 URL 时逐路径段 encodeURIComponent，协议入口只解码一次并捕获格式异常；覆盖中文、空格、井号、百分号和嵌套目录。

### 14. [P2: 静态立绘忽略空闲开关和宿主忙碌状态]

- 位置：`app/src/renderer/components/StaticStage.vue:112-139`。
- 触发：切到静态立绘，关闭“空闲小动作”，或 Agent 持续思考/等待审批超过随机间隔。
- 结果：静态组件自己的 scheduleIdle 只检查情绪池是否为空，不检查 idleActionsEnabled、工作状态、审批、工坊或面板。状态变化只重排计时，之后仍会随机换脸，与 Live2D 的门控不一致。
- 证据：运行真实调度函数，提供“空闲关闭+正在思考+待审批”状态，仍注册 timer，并在到期后写入随机 happy。
- 建议：两种渲染模式共用可空闲判定；关开关/进入忙碌时取消随机展示，恢复空闲后再重新安排。补充减少动态效果的支持。

### 15. [P2: 宿主直连的迟到回复绕过会话隔离]

- 位置：`app/src/renderer/components/DeskpetStage.vue:814-864`。
- 触发：从桌宠发送一条耗时请求，在 CLI 返回前切换宿主或收到新 session_bind。
- 结果：RuntimeCommandController 会清理旧流，但 sendText 中等待的独立 Promise 不在其控制下；旧请求返回后直接 showChatMessage、TTS 和触发开心预设，把旧会话回复插入当前桌宠表现。即使修复跨窗口宿主同步，该问题仍需单独处理。
- 证据：运行真实 sendText，桥请求未结束时切换当前宿主，再返回旧回复；旧回复仍被加入气泡。
- 建议：发送时捕获 host/session/turn 令牌，回执、播报与动作全部检查归属；切换时取消或忽略旧请求。语音转写后的 autoSend 同样需要捕获原目标，避免改发当前的新宿主。

### 16. [P2: 循环动作约五秒后停止续播但仍显示处于循环]

- 位置：`app/src/renderer/composables/useMotionPriority.ts:56-70,83`。
- 触发：以非 Idle 层播放 `loop=true`，持续超过五秒。
- 结果：统一释放 timer 把 currentLayer 清空；motionFinish 回调要求 currentLayer 仍等于原 layer，从此不再续播。looping 标记没有同步清除，`isLooping()` 仍为 true。与 MCP 对“直到其他动作或交互才停止”的说明不符。
- 证据：生产控制器，开启 Reply 层循环，触发 5000ms timer 再触发 motionFinish，play 次数仍为 1，isLooping 仍为 true。现有循环测试没有跨越层级释放 timer。
- 建议：循环所有权不能被非循环的超时释放；按真实结束/显式停止更新层级与 looping。覆盖短动作多轮和单动作超过五秒。

### 17. [P2: 宿主直连依赖开发机绝对安装路径]

- 位置：`app/src/main/host-bridge.ts:59-65,276-286,307-340`。
- 触发：在没有相同 D 盘目录的电脑使用 ZIP，或 DSH/OpenCode/ZCode 安装到了其他目录；Claude Code 通过不同于固定 npm 目录的方式安装。
- 结果：即使宿主插件已正常登记会话，发送消息仍被判定“没有找到 CLI”。正式包能启动不等于桌宠输入功能可移植。
- 证据：生产路径常量及存在性检查静态核对。另读本机 `codex queue --help`，确认当前已安装 CLI 确实支持 `--thread/--message`，没有把这部分已验证有效的语法误报为 bug；没有向任何真实宿主发送消息。
- 建议：建立明确的可执行文件发现/用户配置或插件登记机制，校验目标与版本；用非 D 盘、标准用户与无开发环境的 Windows 实机验证。

## 文档与较小体验问题

### 18. [P3: 用户指南与候选包首次阅读说明落后于当前行为]
