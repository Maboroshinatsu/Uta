# Uta 全项目评估：能力边界、实际问题与后续顺序

日期：2026-10-28。读者：项目维护者及后续开发会话。

## 结论与产品边界

Uta 已形成较完整的桌面表现、宿主连接、输入输出及本地待办链路。当前主要短板是跨模块行为的一致性、跨模型和真实宿主的验证，以及备份与说明的完整性。继续增加人格、记忆或独立对话决策，会偏离用户确定的职责边界。

本轮采用用户最新决定，覆盖旧文档与旧评估：

- 每个桌宠选择并绑定一个宿主平台；不再把多个 Agent 共用桌宠作为产品目标或未来建议。
- 角色个性、记忆、对话内容和任务决策由宿主负责。Uta 接收表达意图，呈现动作、声音、气泡和交互反馈。
- 本地点按、拖动后的轻反馈可以由 Uta 实现；不能因此推导出必须新增桌宠人格系统，也不需要每次小反馈都请求宿主推理。
- 源码仍有同一宿主下的会话列表及发送目标选择。这是当前实现事实，不应与跨宿主绑定混为一谈。

本轮发现两个可复现的功能问题，尚未修改业务代码：每日提醒跨午夜推迟失效；专注模式未抑制 Live2D 的持续待机微动作。

## 已复现的功能问题

### [P2：每日提醒跨午夜后忽略“稍后提醒”]

位置：`app/src/main/daily-todo-store.ts:72-103`。

复现条件：一条每日 23:55 提醒的未完成待办，23:55 已提醒，选择 10 分钟后；在次日 00:05 计算到期状态。

- 期望：00:05 再提醒，期间保持未处理标记。
- 实际：`currentOccurrence()` 先变为次日 23:55，`isDailyReminderDue()` 在检查 `snoozedUntil` 前因 `now < dueAt` 返回 false；`unhandledDailyReminderIds()` 同样返回空。
- 影响：这次推迟提醒在预期时间不触发，角标也暂时消失；会等到当天正常提醒时间才重新进入到期范围。

使用实际 TypeScript 模块与固定本地时间构造数据，结果：

```text
remindAt     = 2026-10-28 23:55
lastReminded = 2026-10-28 23:55
snoozedUntil = 2026-10-29 00:05
now          = 2026-10-29 00:05
occurrence   = 2026-10-29 23:55
due          = false
unhandled    = []
```

证据：本机 `.tmp/project-audit-20261028/cross-midnight-snooze.json`。这是时间边界复现，不是等待真实午夜得出的结论。

修复方向：将未处理的推迟实例与下一次每日计划区分；到期判断与未处理角标必须使用一致规则。回归至少覆盖午夜两侧、修改原提醒、完成后次日重置，以及推迟超过一天的输入边界。

### [P2：专注模式未暂停 Uta 的持续待机微动作]

位置：`app/src/renderer/components/DeskpetStage.vue:641-655`；`app/src/renderer/services/performance/ambient-state.ts`。

- 专注开关已拦截随机待机动作、状态解说、TTS 和静态立绘待机。
- 但持续表现入口只传 `idleActionsEnabled`，没有结合 `focusActive`，因此 Live2D 仍维持 `ambient.state = idle`。
- 独立 Electron 加载 Hiyori，通过设置窗口的真实模型检查链路取样：专注前后 `suspended = false`，专注后 `focus = true`，仍存在 Uta 的持续头部附加量。

```text
before: focus=false, state=idle, suspended=false, head=-0.0545038629
during: focus=true,  state=idle, suspended=false, head=-0.0138718714
```

证据：本机 `.tmp/project-audit-20261028/results.json` 中 `before-focus` / `during-focus`。结合入口代码可确认专注未覆盖此表现层；样本不用于评判动作是否好看，也不代表应该冻结模型自带的呼吸、眨眼和物理。

修复方向：明确专注下哪些自动表现暂停，把 Uta 添加的待机表现接入同一策略；保留需要用户处理的审批与提醒反馈。不能简单将整个渲染循环停掉。

## 能力边界和维护问题，不能与已复现 Bug 混为一谈

### 备份尚未覆盖完整使用状态

`renderer/services/data-transfer.ts` 的公开迁移包包含设置、预设和校准；项目/日常待办有各自恢复入口。互动偏好位于 `stores/deskpet.ts` 的 localStorage，帧率与自适应偏好位于 `services/render-fps.ts` 的 localStorage，尚未在同一个迁移包内。聊天记录只支持导出。

这不表示当前数据会丢失，而是用户换机或重建 profile 时，不能期待一次迁移恢复所有体验。建议先展示明确的备份覆盖清单，再统一安全的非敏感数据迁移；密钥继续按单独安全策略处理。

### 模型接入仍需要理解目录与适配

已有刷新模型列表、打开目录、模型检查和校准。真正缺少的是面向普通用户的导入闭环：选择模型 → 验证所需文件 → 告知可用动作/通道 → 预览 → 确认启用 → 失败保留原角色。这比新增更多固定姿势更能改善不同模型的可用性。

### 桌面安静策略可以继续统一

已有手动 30 分钟专注、减少动画、语音开关与窗口隐藏。未发现针对全屏应用/固定安静时段的一致自动策略。此项可作为后续可选功能，先修好现有专注规则，再讨论哪些情况下隐藏、静音或仅保留重要提醒；不默认强制读取屏幕内容。

### 宿主操作能力不一致

不同宿主对发送消息、审批和中断的支持有差异。已有连接诊断与发送提示，仍应将每项能力的实际可用状态贯通界面、插件与文档。中断当前宿主任务是可选扩展，必须先获得准确目标和可靠的宿主控制接口，不能猜会话或伪造“已停止”。

### 文档与能力声明已经漂移

- `plugin/README.md:50-57` 仍标 MCP 4 工具，实际为 5；Claude/ZCode/Codex 反向输入仍写“否”，与主进程桥接实现不符。
- `plugin/README.md:70` 仍让用户选择系统语音，但该入口已经移除。
- 根 `README.md:25` 仍称 RP 人设来自 Uta 设置面板，当前实际配置链路在 DSH 宿主插件。
- 路线图早期状态表与后续补充记录混在一起，不能拿前部的“未实现”直接当当前结论。
- `renderer/services/media/` 留有未接入生产调用的旧接口占位；真实 STT/TTS 在其他链路实现。`HookHostAdapter` 的能力声明与主进程发送桥也存在分层差异。应整理单一能力来源，不能看到旧占位就宣布语音/发送功能缺失。

## 建议的实施顺序

1. **先修现有承诺**：跨午夜推迟与专注表现遗漏，补能真实捕获问题的回归用例。
2. **统一使用状态**：明确备份覆盖范围、归一偏好存储与能力声明，修正文档，减少“实现了却看不出来”和“说明有但实际上不可用”。
3. **补真实验收**：选择实际常用宿主与两类代表模型，完成输入、状态、审批、语音、提醒及恢复的一条完整日常脚本；再测唤醒与长时间资源使用。
4. **按价值扩展**：优先考虑模型导入向导，其次可选的自动安静规则；宿主中断等控制能力逐平台确认后再加入。

不建议以桌面人格养成、独立记忆/对话系统或重新支持跨宿主共享作为本轮后的默认方向。Uta 更需要把已有桌面陪伴能力做可靠、易理解、易迁移。
