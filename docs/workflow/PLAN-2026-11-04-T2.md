# T2 方案：Codex 目标读取与参数暴露（2026-11-04）

基线 `main` @ `250f840`。本方案只收录**已经实测**的问题；HANDOFF §4 里未经验证的条目先不放进来。

## 1. T2-A：Codex 目标读取恒失败（已实测，推荐先做）

**现状证据**

- `codex-goals.ts:93` 用 `require('node:sqlite')`；Electron 34 的 Node 没有该内置模块，
  `:135` 的 `catch { return null }` 把失败吞成「没有目标」。
- 本机 `~/.codex/goals_1.sqlite` 的 `thread_goals` 表 **0 行**，所以即使模块存在也读不到东西——
  这条链路在当前机器上是「双重失败」，且外部看不出区别。
- 但 Codex 会把目标写进会话转录：`~/.codex/sessions/2026/11/03/rollout-…-<threadId>.jsonl` 第 256/262/366 行
  都有 `payload.type = "thread_goal_updated"`，`payload.goal` 含
  `objective / status / threadId / createdAt / updatedAt / tokensUsed / timeUsedSeconds`（本机实测 77 字目标）。
- 转录文件名以 threadId 结尾，可直接按 id 定位文件，不需要遍历全部历史。

**方案（零依赖）**

1. `readCodexSessionGoal` 保留 sqlite 主路径（未来 Electron 升级可用）；
2. 主路径不可用或返回空时，按 sessionId 在 `~/.codex/sessions/**` 找 `*<sessionId>*.jsonl`，
   从文件末尾向前扫描，取最后一条 `thread_goal_updated`，把 `updatedAt`（秒）换算成毫秒；
3. 找不到文件时再退化为「最近 N 个转录里按 `goal.threadId` 匹配」，N 取小值避免卡顿；
4. 读失败不再静默：主进程留一条 `console.warn`，返回值契约不变（`CodexGoalResult | null`），
   不改 IPC 与界面，避免牵动宿主计划链路（`todo-store.ts:311-324`）。

**验收**

- 用本机 2026-11-03 那场 Codex 会话：修复前 `hostPlan` 为空，修复后能读出 77 字目标与步骤列表；
- 单测覆盖：正常 JSONL、无目标行、坏行、文件不存在、sqlite 分支抛错 → 均回落到预期结果；
- 性能：按 id 定位文件，禁止全量遍历 sessions。

## 7. T2-C 影响评估（2026-11-04，子代理取证 + 主代理回验）

### 7.1 motion3 混流导出

**现状机制**：导出器把步骤切成 transition/hold 时间片（`motion-exporter.ts:217-257`），按帧采样后
**只输出线性段（type 0）**（`:363-366/:395-397`）；FadeIn/FadeOut 共用单一 `fadeTime`，调用方默认 0；
步骤绑定原生动作时直接抛错（`:203-212`），UI 先在 `SettingsPanel.vue:1636-1644` 拦截并说明原因。

**缺的数据**：运行时只有「模型全部动作曲线 Id 的并集」（`main/index.ts:713-738`）和按文件名的
时长/循环（`motionDetails`，`loader.ts:414-438`）；**没有按动作组的曲线**，也没有按组读 motion3 的 IPC。

**要碰的地方**：①主进程新增「按组读曲线」能力（一次读取 + 缓存，或扩展 diskAssets）；
②把原生曲线按步骤时间轴平移、与步骤采样合并；③统一时长（例：body-led happy 动作 6.4s、步骤合计 4.8s）、
Loop/Fade 只有一份、`Meta` 统计（`:410-427`）、物理通道排除。

**风险（关键）**：同一参数被原生动作与步骤关键帧同时写入时，**谁覆盖谁没有现成规则**——运行时对原生动作
根本不做过滤（见 7.2），所以无法从现有行为反推出一个「忠实」的合并语义。这是产品决定，不是技术细节；
选错会让导出文件与预览不一致。

**工作量**：约 200–400 行 + 测试；难点在时长与冲突规则，不在解析（`compileMotionTrack` 已支持 0/1/2/3 段型）。

**建议**：先回答「同通道冲突谁赢、原生动作比步骤长时怎么截断」再开工；否则维持现状的明确拒绝
（当前不会静默产出坏文件）。

**2026-11-04 用户澄清后收口：不做。** 实际用途是「在另一台 Uta 复用同一套动作/预设」，不是给外部软件用。
现成的「用户预设 → 导出/导入」（`preset-transfer.ts`）已经携带步骤参数、控件、部件与动作组绑定，
导入时按模型 `model3.json` 文件名校验（文件夹改名不影响），按 `hasMotion` 校验动作组（缺失即整包拒绝），
并有 `preset-transfer.test.cjs` 覆盖含 `missing-motion` 的路径。因此无需把预设烘成 motion3；只有「导出给 Cubism/VTS 等外部工具」才需要混流。

### 7.2 首步叠加（结论：不成立，撤销）

原 P1 的推断是「`playMotion` 里 `await` 使状态未切换」。**回验推翻**：pixi 的 `startMotion`
（`node_modules/pixi-live2d-display/dist/cubism4.es.js:4187-4192`）在第一个 `yield` 之前同步
`state.reserve(...)`，`__async` 同步跑到首个 yield，因此 `playMotionWithPriority` 返回时 `reservedGroup`
已就绪；`usePresetController.ts:620` 紧随其后的 `runStep(0)` 拿到非空归属集，**首步会被过滤**。

**真实残留**：归属表 `installed` 只登记大肥鱼运行时生成的动作，普通 `.motion3.json` 动作在任何步骤都不参与
过滤。本机 14 个 `deskpet-presets.json` / 173 个预设中，绑定动作的为 **0**，属潜在路径。

**建议**：不修，只保留记录；若将来用户开始绑定原生动作并报告叠加，再按「动作启动前声明通道」立项。
